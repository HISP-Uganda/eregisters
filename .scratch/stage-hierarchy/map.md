Label: wayfinder:map

## Destination

The analytics line list's parent/child stage joining stops assuming any stage can pair with any other. Program stages get a per-program, admin-configured, many-to-many allow-list of legal parent→child pairs, shared across all users via a new DHIS2 dataStore key (`dataStore/eregisters/stage-hierarchy`), synced through a new pull actor mirroring the existing `pullUIConfig`/`ui-config` pattern in `src/machines/sync.ts` (new Dexie table, new `fromPromise` actor chained into `metadataSync`, new live-query hook, admin-route write-back via `engine.mutate`). A new admin screen under `/admin` (reusing the existing `ALL`-authority gate) lets an admin define these pairs per program.

The line list's stage picker is **replaced**: instead of "pick a main stage, then child stages," the user picks **one stage**, and its role is inferred from configuration — if it has configured children, those flatten in one-to-many (today's existing behavior, unchanged); if it has a configured parent, that parent's data elements flatten in one-to-one (new, via the event's existing `event.parentEvent` FK — already inherently 1:1 at the data level); a middle-of-chain stage with both a configured parent and configured children shows both joins on the same row. Scoped to **one hop only** in each direction — no multi-level chain walking. A child stage with multiple legal parents (allowed in the config UI, since pairs are many-to-many) still resolves at analytics-build-time via the event's single real `parentEvent` pointer — no column-group explosion for multiple possible parents. Before any admin configures anything for a program, that program's line list keeps behaving exactly as it does today (fully unrestricted) — nothing breaks on rollout. The config is cached locally (Dexie) and usable offline, like other metadata.

Reached when: the admin screen exists and can save/load per-program pairs; the line-list picker uses that config to drive one-to-many / one-to-one / both joins; `parent-event-dataset.ts` produces one-to-one parent-flattened columns when a child stage is picked; and nothing regresses the existing one-to-many flow for programs with no pairs configured.

- Every ticket session should invoke `/grilling` and `/domain-modeling` when in doubt; prototype-typed tickets should invoke `/prototype`.
- Key fact: the parent/child join is via `event.parentEvent`, a real per-event DHIS2 FK — a child event always has exactly one actual parent event. "One-to-one when starting from the child" falls out of this for free; the config only decides which pairings are *legal to offer in the UI*, it doesn't change how the join itself resolves at runtime.
- Existing `AnalyticsFilters` shape (`programId`, `mainStageId`, `childStageIds`, date range fields) and the `returnSearch`/`restore` URL round-trip built earlier this session (in `src/routes/analytics.tsx`) both currently assume the old two-step picker — expect this effort to change that shape; the URL-restore code already tolerates unknown/missing fields via try/catch, so no explicit migration path is required, just awareness during implementation.
- `useMetadata().program` is a single object, not a list — this app runs against exactly one active tracker program at a time, not a program switcher. So "per-program" config (Destination) degenerates to a flat array for that one program, no `Record<programId, ...>` wrapper needed (see [Admin screen for configuring stage parent/child pairs](issues/01-admin-stage-pair-config-screen.md)).

## Decisions so far

- [Analytics filter/dataset shape for stage-hierarchy-driven joins](issues/02-analytics-filter-dataset-shape.md) — `mainStageId`/`childStageIds` collapse to `selectedStageId` + a `childStageIds` subset now scoped to only that stage's legal children; new one-to-one data uses a distinct `linkedParent.<stageId>.*` column prefix (existing `parentEvent.*` prefix is untouched, no breaking rename); the column registry detects which legal parent stage(s) are actually realized in the real data (not the full configured set) and builds one flat (non-slotted) column-group per realized stage.

## Out of scope

- Multi-level (2+ hop) chain joins (e.g. a grandparent stage's data elements) — ruled out; one hop only per this effort's destination.
- Any new permission tier for configuring stage pairs beyond the existing `/admin` `ALL`-authority gate — ruled out, reuses the existing gate.
- Conflict resolution for concurrent admin edits to the shared dataStore config beyond whatever `ui-config` already does today (i.e. none, last-write-wins) — ruled out, not a new requirement for this effort.
- Unbounded column-group growth tied to *configured* legal-parent cardinality — ruled out; refined by [Analytics filter/dataset shape for stage-hierarchy-driven joins](issues/02-analytics-filter-dataset-shape.md) to: one `linkedParent.<stageId>.*` group per parent stage actually *realized in the real data* (typically one), not one per legally-configured parent — bounded by data diversity, not config breadth, and each row still populates only the group(s) matching its own actual parent.
